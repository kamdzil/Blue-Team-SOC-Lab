# Phase 6 — Sysmon Integration & Threat Investigation

## Overview

In this phase, I expanded my Blue Team SOC home lab by integrating Microsoft Sysmon with Wazuh SIEM.

The objective was to improve Windows endpoint visibility by collecting detailed process activity logs, forwarding them to Wazuh, and investigating suspicious security alerts.

I successfully configured Sysmon monitoring, verified event collection, and investigated alerts associated with PowerShell and Windows security configuration tools.

## 1. Sysmon Installation and Verification

I downloaded Microsoft Sysmon from the official Microsoft Sysinternals distribution and extracted the executable files using PowerShell.

I installed Sysmon on my Windows 11 endpoint using:

```powershell
.\Sysmon64.exe -accepteula -i
```

After installation, I verified that the service was operational:

```powershell
Get-Service Sysmon64
```

The service returned a **Running** status, confirming that Sysmon was successfully installed.

## 2. Sysmon Event Log Verification

After installing Sysmon, I verified that it was collecting Windows endpoint activity.

I retrieved the 10 most recent Sysmon events using:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 10 | Select-Object TimeCreated, Id, ProviderName
```

The results confirmed that Sysmon was recording:

- **Event ID 1:** Process Creation
- **Event ID 5:** Process Termination

This demonstrated that Sysmon was actively monitoring Windows process execution and termination.

## 3. Wazuh SIEM Integration

To enable centralized Sysmon monitoring, I configured the Wazuh agent to collect events from the Sysmon Operational event channel.

I opened the Wazuh configuration file:

```powershell
notepad "C:\Program Files (x86)\ossec-agent\ossec.conf"
```

I added the following configuration inside the `<ossec_config>` section:

```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```

After saving the configuration, I attempted to restart the Wazuh agent. The initial restart encountered a service error, which I resolved by starting the agent and verifying that its status returned to Running.

```powershell
Start-Service WazuhSvc
Get-Service WazuhSvc
```

I then opened the Wazuh dashboard and navigated to **Threat Hunting → Events**.

I searched for Sysmon events using:

```text
data.win.system.channel:"Microsoft-Windows-Sysmon/Operational"
```

Wazuh successfully displayed 20 matching alerts from `Windows-SOC-Agent`, confirming that Sysmon logs were reaching the SIEM and triggering detection rules.

The alerts included:

| Rule ID | Description | Severity |
|---|---|---|
| 92031 | Discovery activity executed | Level 3 |
| 92066 | SecEdit.exe launched from a suspicious location | Level 4 |
| 92021 | PowerShell used to delete files or directories | Level 3 |

## 4. Security Alert Investigation

After confirming that Sysmon events were reaching Wazuh, I investigated an alert generated by **Rule ID 92066**.

The alert identified `SecEdit.exe`, a legitimate Windows security configuration utility, being executed through PowerShell.

I expanded the alert in Wazuh Threat Hunting and reviewed its process information.

### Investigation Findings

| Field | Result |
|---|---|
| Wazuh Rule ID | 92066 |
| Severity | Level 4 |
| Endpoint | Windows-SOC-Agent |
| Executable | SecEdit.exe |
| Parent Process | powershell.exe |
| Integrity Level | SYSTEM |
| Activity | Windows security policy export |

The captured command was:

```powershell
C:\WINDOWS\system32\SecEdit.exe /export /cfg C:\WINDOWS\TEMP\secpol.cfg
```

This command exports local Windows security policy settings into a configuration file.

Although `SecEdit.exe` is a legitimate Windows utility, security policy enumeration may also be associated with reconnaissance activity.

I therefore investigated the process context rather than immediately assuming the activity was malicious.

## 5. Identifying the Source of the Alert

To determine whether the activity was legitimate, I examined the Wazuh Security Configuration Assessment (SCA) dashboard.

I discovered that Wazuh had performed a security configuration scan against my Windows 11 endpoint.

The scan completed on **November 11, 2026, at 2:54:05 PM**, matching the time period of the Sysmon alerts.

The SCA checks also displayed the same PowerShell and `secedit /export` commands identified during the alert investigation.

This provided strong evidence that the suspicious activity originated from Wazuh's security configuration assessment rather than an external attacker.

### Security Configuration Assessment Results

| Result | Count |
|---|---|
| Passed | 122 |
| Failed | 351 |
| Not Applicable | 9 |
| Total Checks | 482 |
| Overall Score | 25% |

The assessment used the **CIS Microsoft Windows 11 Enterprise Benchmark v3.0.0**.

Although the endpoint received a 25% compliance score, this represents benchmark configuration compliance rather than a direct measurement of whether the system is compromised.

## 6. Investigation Conclusion

Based on the available evidence, I determined that the investigated `SecEdit.exe` activity was associated with legitimate Wazuh security auditing.

The matching timestamps, executable commands, and SCA check definitions supported this conclusion.

I classified the activity as a **benign positive**, meaning Wazuh detected activity that matched a security rule, but the investigated behavior was authorized rather than malicious.

This investigation demonstrated the importance of analyzing process details, correlating timestamps, and validating alerts before escalating a potential security incident.
